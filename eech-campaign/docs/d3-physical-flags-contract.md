# D3 physical flags: the per-entity UPDATED / MOVED / ROTATED word (characterisation, EEDCS-49)

Status: **characterisation only. No production flag moves. UNREVIEWED.** (Section 7 adds the first real immediate-consumer control.) This records what the ORIGINAL code does, from the source and from a real-C control, so the next production move is concrete. It is the named required blocker `ENV-PHYSICAL-FLAGS-RAWWORD-CONTRACT-1`
(the "UPDATED truth/domain/guide contract" that `needed-consumer-api-disposition-open-rows` and `entity-object-collision` already declare missing). Nothing below is a design, an ABI, a trait or a layout; unknown facts stay unknown.

Evidence: `csrc/eech_physical_flags_check.c` + `tests/physical_flags.rs` (feature `physical-flags-check`, 199 expectations over the REAL getter, setter, flag arrays and `update_client_server_entities`), and the source census `tests/physical_flags_guard.rs`
(text patterns, not behaviour). The control loads no retail data, boots no campaign and runs no consumer body.

## 1. What the word is (source facts, verified against the code, not the English labels)

- **Not a per-entity field.** It is three GLOBAL bit arrays in `special/update/up_update.c`: `moved_entities`, `rotated_entities`, `updated_entities`, each `unsigned int [MAX_NUM_ENTITIES / 32]` with `MAX_NUM_ENTITIES = 131072 * 4 = 524288` (16384 words, 65536 bytes each).
  The "per-entity 32-bit word" is the 32-bit WORD OF THE ARRAY that holds the entity's bit: word = `entity index >> 5`, mask = `1 << (entity index & 31)` (`mobile/mb_int.c`). The key is the **entity heap index alone** (`entity - entities`): no type, identity, host id or life is part of it.
- **Setter** (`INT_TYPE_UPDATED|MOVED|ROTATED`, local setter only; no client/server setter is installed): `ASSERT (value == TRUE)` then `array [word] |= mask`. TRUE-only; the commented-out FALSE path of `up_update.c` was replaced by the reset below. With assertions off a FALSE value would still OR the bit (source fact, not run).
- **Getter**: `value = array [word] &= mask`. Observed with the real code: it returns the entity's **MASK** (a power of two; `INT_MIN`, i.e. negative, for bit 31), not 1; it **clears every OTHER entity's bit in the same 32-bit word** (so a read of one entity destroys up to 31 neighbours' flags and the answer depends on read order);
  it does **not** clear the entity's own bit (a second read returns the mask again). A getter of an UNSET entity returns 0 and clears its set neighbours. To an `if (getter)` consumer any non-zero value, negative included, is true; only bit 0 equals `TRUE`.
- **Reset**: `update_client_server_entities` does `memset (updated_entities, 0, MAX_NUM_ENTITIES / (sizeof (unsigned int) * 8))` once per update ITERATION before the update loop. The count is a number of BYTES: 16384 of the 65536 bytes, **a quarter of the array**. Entity indices **0..131071 are reset; 131072..524287 are NEVER reset** (once set, an UPDATED bit above the extent SURVIVES every reset; it is cleared only by the same destructive `&=` getter reading ANOTHER entity of its 32-bit word, or by another actual overwrite). MOVED and ROTATED are reset by the same quarter-memset only behind `tacview_is_logging () && tacview_reset_frame ()` (not exercised; with logging off nothing resets them). This is a LEGACY DEFECT preserved as a compatibility fact; it is not repaired here.
- **Set sites**: UPDATED is set once per update-list member AFTER `update_client_server_entity (en)` (`up_update.c`), so during an entity's own update its bit is still clear (below index 131072). MOVED/ROTATED are set by the movement code after a step (`hc_move.c`, `fw_move.c` rotated, `rv_move.c` rotated, the hosted `rv_hostmv.c` after the host's step, the gunship `dynamics.c`).
- **Domain**: installed by `overload_mobile_functions`, called for the aircraft (fixed wing, helicopter), vehicle (routed, ship, anti-air, person), cargo and weapon families. A fixed OBJECT keeps the default function (a read of it would stop the engine). `INT_TYPE_MOBILE_MOVING` (read by the fixed-wing and routed updates for the Tacview `moved` argument) is installed by BOTH the aircraft (`ac_int.c` 853/1225) and the vehicles (`vh_int.c` 748/1101) and is a DIFFERENT field, distinct from these arrays.

## 3. A real contract mismatch found at the boundary (source-derived, reachability UNKNOWN)

`gd_supply_arrival.c` copies the RAW getter value into the supply-arrival descriptor (`descriptor.updated = get_local_entity_int_value (member, INT_TYPE_UPDATED)`, a `c_int`), and the Rust side validates it with `checked_bool` (`eech-engine/src/lib.rs`), which accepts exactly 0 and 1
and otherwise returns `invalid updated flag N`. The neighbouring flag of the same function IS normalised (`... ? TRUE : FALSE`). So a member whose UPDATED bit is set with a mask other than 1 (any entity index not divisible by 32) is a descriptor error. Whether this is reached: during the member's own update its bit is clear below index 131072, but at index >= 131072 the bit SURVIVES the resets (the quarter-memset), so such a member can still read its mask on later iterations until a destructive read of another entity of its word (or another overwrite) clears it; the same getter acts at every index, so survival of the reset is not permanence, and how often the mask is still there when the descriptor is built is not measured. The shipping runs that passed may simply never have met an index >= 131072 mask != 1 on this path: **UNKNOWN**. This is a defect candidate, not fixed and not claimed reached.

## 4. Boundary: what is physical, what is Core, and what is NOT yet shown

Root's feedback of 15:50 (`Root-physical-flags-feedback-20261107-1550.json`, read before the freeze) fixes the constraints this section obeys: the accepted byte-identical behaviour stays mandatory; **the destructive `&=` getter and the quarter-memset cannot be declared outside the observable behaviour to simplify a move**; no boolean normalisation and no supply-descriptor fix is authorised
by this work; MOVED and ROTATED are NOT scoped out of whole D3; no preselected design.

- **Physical truth**: the three words record whether a mobile entity was stepped (UPDATED, read by the collision pass-through, the fixed-wing pass-through and the supply descriptor) or moved/rotated (MOVED/ROTATED, read by the Tacview writers). They are the physical RECORD of a step, and a move to the host may not leave a second authoritative store inside the Core. MOVED/ROTATED are observational but remain part of the required responsibility.
- **Core**: update scheduling (which entities, in which order, how many iterations), when each update starts and ends, the decision to call a consumer, the supply/arrival POLICY and the Tacview writers' own decisions.
- **What a host-owned version must reproduce, because the current facts make each observable** (none may be simplified away): (1) the complete RAW return of the getter (the mask, negative for bit 31), not a boolean; (2) the CROSS-ENTITY destructive read: a getter of one entity clears the other entities' bits of its 32-bit word, so any entity's answer depends on the order and extent of other entities' reads, and the reads of the three consumers are interleaved with other entities' updates;
  (3) the reset EXTENT (UPDATED: indices 0..131071 once per update iteration, never above; MOVED/ROTATED only behind the Tacview frame reset, with the same quarter extent); (4) INDEX REUSE (the key is the heap index alone and a reused slot inherits the bit); (5) the ORDER of the set (after the entity's own update) against the reads of the consumers.
- **A simple "has this entity been stepped" truth service plus a Core mirror is NOT demonstrated sufficient** by these facts: it cannot carry the raw mask, the neighbour effect, the reset extent or the index-keyed reuse. It is not proposed and nothing here preselects it. The key question the review must decide is where the word's WHOLE store (arrays, setter, getter, reset) lives and how its heap-index key (the legacy key; the host's identity is the roster host id) crosses the boundary without a second store.
- **Source-derived defect candidate, explicitly UNCONFIRMED and SEPARATE**: the supply-arrival descriptor copies the raw mask into a field the Rust side validates as 0/1 (section 3). It is not fixed, not normalised and not part of any proposed move; its reachability is unknown.

## 7. The first real immediate-consumer control (`csrc/eech_physical_flags_consumer_check.c`, feature `physical-flags-consumer-check`, 56 expectations)

The ORIGINAL fixed-wing `response_to_check_mobile_reached_guide` (`fw_msgs.c` 396..518) is called through the REAL message dispatch (`notify_local_entity`, `message_responses [FIXED_WING][CHECK_MOBILE_REACHED_GUIDE]`, installed by the engine's `overload_fixed_wing_message_responses`) over hand-made fixed-wing and guide records of the engine's own types, reading its ACTUAL collaborators (the real LANDED / DISTANCE / VELOCITY / motion / position getters,
the real guide criterion accessors, `get_delta_time ()`, `get_3d_perp_dist_of_point_from_line`). Declared hand-made: the pool slots and their raw `fixed_wing` records (NAVIGATING, distance 10, velocity 20, position (10, 5, 0), motion (-20, 0, 0)), one GUIDE entity with a valid RADIUS criterion (6) and the WEAPON_VECTOR criterion off (so the `frand1` path is never entered), `system_delta_time`, the SERVER comms model, an empty update list for the real reset.
Everything modified is saved and restored. Measured with the original code:

- **The raw word is read only on the pass-through branch** (not landed, range > radius, range - velocity <= radius): the three early returns (landed, range inside the radius, range - velocity beyond it) leave every flag word, a set neighbour included, untouched.
- **On that branch** an UNSET flag selects the future position and a SET flag (any raw mask: bit offsets 0, 1, 2, 30 and 31, INT_MIN included, no boolean conversion) the previous position; with the coherent trajectory the first returns TRUE and the second FALSE; a smaller radius or a shorter delta time changes the real arithmetic's result with the flag unset.
- **The read is the destructive `&=`**: it keeps the entity's own bit and CLEARS its word-mates, so the second of two consumed entities of one word sees a different flag than it was set with, and the result depends on the call ORDER (A then B gives FALSE, TRUE; B then A the mirror). An unset receiver's consumer call destroys a set neighbour's flag.
- **Above the reset extent** (index 400000): the set bit survives two real resets and the consumer still reads it (repeated own-bit reads change nothing), but a consumer read of its word-mate clears it, after which the entity is unset: survival of the reset is not permanence. Below the extent (index 100) the real reset clears it.
- **A source fact the control measured, not a design**: the response reads the guide position with `get_local_entity_vec3d (receiver, VEC3D_TYPE_GUIDE_POSITION, ...)` on the FIXED-WING receiver; only a GUIDE registers that vec3d type, so the receiver's table keeps the engine's DEFAULT getter, which writes the zero vector. In the pass-through branch the original therefore measures against the world origin, not the guide. Preserved, not repaired.
- A slot given a fresh raw record keeps the flag bit of its index (keyed by the index alone; no claim about the real heap's reuse).

**Not claimed**: the shipping profile routes the arrival to `campaign_supply_arrival_check` / `campaign_radius_arrival_check` first (`guide.c`), so this original response is the arrival the profile retains for the other cases; the other consumers are not run (section 5); helicopters, vehicles and ships (their own responses) are not run; the setter with FALSE; strict-C, `-O2` or signalling-NaN behaviour (the bit-31 observation is the supported compiler profile's, not a portable guarantee).

**How the key crosses the boundary without a raw heap index.** The key of the original is the heap slot alone (word = slot >> 5, bit = slot & 31). The host never receives a slot, a pointer or a layout. The campaign derives the entity's GROUP (slot >> 5) and LANE (slot & 31) privately (`mb_hostmodel.c`, `flag_group_key`), asks the HOST once per group to open it (it issues an opaque key, `f` and decimal digits, never a roster key; fact 0 states whether the group lies inside the original's reset extent: the word index is below the number of words the byte-counted `memset` clears, a quarter of the array, slots 0 to 131071), and thereafter names a group by that key and an entity by its lane (0 to 31, the bit of the word, which the original's raw mask makes observable). The campaign's table holds identity only (a key per group, the empty text until used), never a bit, mask or word, and nothing answers from it. Grouping is the campaign's (it is a property of its heap); the host never infers it from host-identity adjacency.

## 9. The two source findings of the consolidated review and the collision consumer control (Task49 correction batch; candidate, UNREVIEWED, native UNRUN)

**ENV-PHYSICAL-FLAGS-KEY-CAPACITY-1 (fixed).** The flag key domain is decided as a WHOLE before any byte is copied (`flag_key_is_valid`, `mb_hostentity.h`): `f`, a first digit 1 to 9, further digits, at most `CAMPAIGN_ROSTER_KEY_MAX` (20) bytes before the NUL, which is the size of every identity slot of the campaign's cache (`char [CAMPAIGN_ROSTER_KEY_MAX + 1]`). ## 10. The public host-owned Lua -> module -> host witness of the flag store (Task49; candidate plan and driver, UNREVIEWED, native UNRUN)

This is the next required gate of `ENV-PHYSICAL-FLAGS-HOST-STORE-NATIVE-ACCEPTANCE-1`: not another control of the C binding, but the path the product ships. A host-owned Lua script boots the public native module (`require ("eech_dc")`, `dc.boot`, `engine:frame`), the real campaign code asks THAT host for every UPDATED / MOVED / ROTATED word through the one bridge `Engine::boot` installs (scan phases 19 GROUP, 20 SET, 21 READ, 22 RESET), and the reference host's real provider (`host.model`, whose `FlagStore` is the store) answers. The driver is `crates/eech-world/lua/physical-flags-witness.lua`; **no product C or Rust changed** (the existing 020 ordinary and Original binaries are the plan's binaries). Root executes it natively after the SAME source review; nothing here is a native result.

**What it observes (and counts apart).** Every flag question and answer as the exact grammar of the public C bridge. *Attempts* are questions the host received, *answered* the provider's whole replies, *accepted* the unaltered replies the engine went on after (its next host callback, or the frame returning without a fatal): an altered reply is never an accepted transaction. The *backing check* is an oracle over the OBSERVED traffic only (never a second store the campaign could use): the destructive `&=` semantics rebuilt from the sets, reads and resets the campaign made. A READ must answer the lane's mask when its bit was set since the last reset of its array and no word-mate's read destroyed it, otherwise 0; a RESET clears the array of the groups opened as eligible and states their number; a group's key is new. A difference is the HOST's fault (a reply fault), never an intervention. The driver adds no question of its own, never searches for an actor, window or seed, and never alters a campaign decision.

**Modes (one bounded process per mode, a fresh verified retail root, the report created exclusively).** `flags_original` runs the ORIGINAL-solver profile (the `eech-dc/collision-fixture` build): the campaign keeps its own arrays and the host is never asked; it is FAILURE if it was asked. `flags_control` is the hosted profile with nothing altered; with `original=<its report>` it is PAIRED (same scenario, seed, frame, duration, effective campaign and map). It runs until the first read that follows an UPDATED-asking candidate decision has been consumed, or the duration ends; PASS needs an accepted group, set and reset, no fault and no backing difference, and reports the reads it reached. Every other mode needs `control=<the successful PAIRED control>` and is credited ONLY with the one eligible intervention actually made at the control's own step (ordinal, frame and the attempts of every phase before it equal the control's) AND the engine stopping at exactly the mode's marker after it:

| mode | the single fault | the engine stops at |
|---|---|---|
| `<group, set, read, reset>_withheld` | the host raises | `entity_scan.callback` |
| `<group, set, read, reset>_malformed` | two patterns instead of three | `entity_scan.answer` |
| `<group, set, read, reset>_wrong_state` | `height` for a flag question | `entity_scan.state` |
| `group_bad_key` | a 21-byte key (the identity slot holds 20) | `flag.key` |
| `group_duplicate_key` | the SECOND group is issued the first group's live key (a wrong identity) | `flag.key` |
| `group_wrong_eligibility` | the eligibility echoed the other way | `flag.answer` |
| `set_wrong_lane`, `read_wrong_array`, `reset_wrong_array` | another lane or array echoed | `flag.answer` |
| `set_wrong_word`, `read_wrong_word` | a raw word that is not the lane's mask (nor, for a read, 0) | `flag.word` |
| `read_changed` | a VALID changed host answer: the first read that follows an UPDATED-asking candidate decision is answered the other way (0 for the mask, the mask for 0) | none: the campaign must CARRY it |

`read_changed` is the "host observations actually influence the campaign" evidence at the one consumer it can observe without a hook: the campaign's moving-candidate sweep states UPDATED to the host's next candidate question as 2.0 (word non-zero) or 1.0 (word zero) (`mb_hostoffer.h`), and PASS needs that question (the very next one, the same candidate, every other fact as before) to state it the way the CHANGED word says and not the way the host's own word said. The control records the same relation unaltered, so a campaign that ignored the host's word would fail the control first.

**Verdicts.** PASS, FAILURE and UNREACHED are distinct and UNREACHED is never a pass. A fatal before the intervention (even at the mode's own marker), no fatal after it, another marker, a request or reply fault or a backing difference is FAILURE and takes precedence over a clean UNREACHED; an event the control never reached refuses the mode before any boot; a trajectory that differs from the control's aborts with no intervention. A control that reached no consumable read still passes for group, set and reset and refuses `read_changed`.

**Commands** (the 020 binaries and the established finite default plan that Root's unchanged-default 020 runs completed natively, ordinary and Original: `lebanon_retail`, `hours=0.001` (35 frames, 3.5 s), `frame_ms=100`, `seed=1`, a fresh verified retail root per process; never chosen by what a run reached; the regression pack's `hours=3` is a longer window a caller may name before a launch, with every report of a family at the same one): `eech-world.exe lua/physical-flags-witness.lua root=<fresh root> out=<new report> mode=<mode> hours=0.001 [original=<flags_original report>] [control=<flags_control report>]`. Order: `flags_original` (Original profile binaries), `flags_control original=...` (ordinary hosted binaries), `read_changed control=...`, then the 20 refusals with the same control. The driver is staged beside the binaries from its frozen literal (the 020 payload's own `lua/` holds the older scripts only).
