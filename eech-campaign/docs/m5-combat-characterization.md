One seed, one scenario and one run are what the census below is: a path it did not reach is declared unreached, not covered. The ownership rule is the migration ledger's: the host owns the physical world and the physical execution of combat (what a hit does to a target's health, how far a blast reaches and how it falls off, when a target is destroyed); the campaign owns who fought whom and why, credit, loss accounting and consequences. ## The observer (feature `weapon-fixture`, never shipping)

`entity/mobile/mb_cmbfx.h` hooks (empty without the feature, arguments discarded) in `damage.c`, `explosn.c`, `mb_msgs.c`, `fixed.c`, `en_msgs.c`, `en_heap.c` and the six `*_updt.c` files, and `csrc/eech_cmb_fixture.c`. Every hook only reads.

* **Collisions.** Sixteen entity kinds have a registered collision handler and all sixteen are wrapped, by one wrapper, whenever the message responses are initialised (the wrapper is installed at the end of `initialise_entity_message_responses`, which first resets every response to the default and registers them again); `notify_local_entity` (which the `eech-sys` crate extracts verbatim) is untouched. The wrapper reads the damage modifier (from a copy of the argument list) and the receiver's health ONLY for the thirteen HEALTH-BEARING kinds (the other three, a bridge, a cargo and a weapon, are counted only) whose handlers read that argument and hold a damage level. A bridge is notified by its segments with NO fourth argument and holds no damage level, and a cargo and a weapon hold none either: for those three the wrapper only counts the delivery (`cmb-unobserved`) and passes the original arguments through untouched, so it neither reads an absent argument nor mislabels a health of 0 as fatal.
* **Why the report says 32 wrapped handlers.** `wrapped_collision_handlers` is a CUMULATIVE count of installations, not a count of distinct kinds. `initialise_entity_system` and `reinitialise_entity_system` (`en_init.c`) each call `initialise_entity_message_responses`, which resets all responses to the default before registering the sixteen again, so each call wraps sixteen fresh handlers. The report already says 32 at boot, before any frame, which is what two initialisations of sixteen kinds give. This is read from the source and the counter; the number of initialisation calls is not counted separately by this build (a later build could add that counter, which would be a new product identity; it is not needed for any claim here).
* **Identity.** The receiver is identified across its handler by a fixture-private generation of its slot, advanced by a hook where the entity heap frees the slot (`set_free_entity`, `set_free_local_entity`); a slot freed during the handler is reported as destroyed and read for nothing else, so a slot reused by another entity during the handler is never read as the receiver.
* **Nesting.** Frames are a table of eight; every access is guarded, the real depth is retained (`depth_max`), a frame beyond the table is counted (`depth_overflow`), never written, and makes the trace report `trusted=0`.
* **Blast.** A blast call belongs to the explosion invocation it runs inside (hooks around the kill-code switch), not to a weapon's address: a land hit's second call is `with_repeated_blast`, two separate invocations by one weapon address are not.
* **Damage application.** Every entry of `damage_client_server_entity` has exactly one exit (no weapon, invulnerable, or done) and the report says whether they balance.
* **Timed health.** The six timed rolls are observed as attempts with the draws the original's condition took and, when they fire, the health they leave, in the original's order (`timed_hash`, `order_hash`).

The shared random stream is observed by the number of draws only.

It reports six ordered hashes (`damage`, `collision`, `blast`, `repair`, `timed`, `order`: the order the categories happened in), counters per entity kind (collisions, direct versus blast, applied, no damage, invulnerable, fatal, destroyed, already dead, damage sum and maximum, blast candidates, in range, notified, rocket kills), capability counters (real weapon versus forecast, armour-penetration versus splash versus none, draws, player targets, multiplier moved the result), per-warhead rows, blast calls by kill code, and an ordered event log of every collision, blast and repair. Through `engine:cmb_trace ()` and `engine:cmb_events ()` of the fixture module; `lua/combat-characterization.lua` runs the campaign through the public host path and writes the checkpoints (default every 60 s) and the final report as JSON lines.

Typing issue found in the real trace by root, and its disposition. The first parser protected hash WORDS (`damage collision blast repair timed order`) from being read as numbers. `blast` is also a COUNTER in every `cmb-kind` row, so the original f41 run wrote `"blast":"69"` (a decimal string) there, while `cmb-hash blast` correctly stayed a 16-hex string. No value was lost; every other counter was a number. The fix is in the shared parser, `lua/combat-report.lua`: a hash is protected only as a field of the `cmb-hash` event, so `cmb-kind blast` is a number. It is proved by `tests/host_callbacks.rs`, which loads that same parser on a synthetic report holding both `cmb-hash blast=0000000000000255` and `cmb-kind blast=69` (and a `blast` with leading zeros as a counter), asserts `"blast":69` and `"blast":"0000000000000255"`, and keeps all six hashes lossless; it failed before the change (`checks/cargo-test-46-typed-red.log`) and passes after (`cargo-test-46-typed-green.log`). The kept original raw trace is NOT rewritten and `natural-01` is not rerun for a format correction: it is the LEGACY schema, and `tools/combat-trace-audit.py` declares that (it accepts either schema, fails a mixed trace, fails any other non-numeric cmb-kind counter, and fails a legacy trace under `--require-corrected-schema`, which a future clean fixture build with the corrected Lua and the witness should satisfy). Root's independent completion record agrees with the audit: 6,440 events with sequence 1..6,440, 234 damage entries equal to 234 exits, all post-run inputs and exports unchanged.

## Controlled witness for the unreached paths (DESIGN, awaiting review; not built, not run)

`csrc/eech_cmb_case.c` (fixture only) and `lua/combat-case.lua` put the unreached paths to the ORIGINAL campaign, one case at a time, through the campaign's own functions; the observer records, and the audit's difference of the before and after reports is the evidence. Each case sets a declared PRECONDITION and then calls the campaign's own entry point; the handler, the damage function, the capability arithmetic and its draw, the health write, the fatal decision, the credit and the explosion effect are the original's. Nothing is mirrored and no physics is moved.

| Case | Precondition set by the test | Campaign entry called | Unreached path it targets |
|---|---|---|---|
| collide | the n-th living entity of a kind (entity-list order); a REAL weapon launched through the Task45 case launch from a host-identified launcher that really carries the weapon; a modifier (0.0 direct, 0.5 blast range) | `notify_local_entity (ENTITY_MESSAGE_COLLISION, receiver, weapon, modifier)` | collisions on OBJECT, PERSON, PYLON, SCENIC, SITE, SITE_UPDATABLE; both arithmetic branches by two weapon classes; the control kind (ROUTED_VEHICLE) for comparison with the natural events |
| collide, weaponless | the same receiver, no weapon | the same notification with a NULL sender | the no-weapon exit of the damage function and each handler's no-aggressor branch (the path a debug event takes) |
| blast | a real weapon placed 5 m from the receiver, with a kill code (land; and once on target, which also links the weapon to the receiver) | `create_client_server_weapon_killed_explosion_effect`, then the destruction the weapon's update makes | the blast reaching a kind (candidate in range, collision notified), the land hit's double blast, the exclusion of the direct-hit target |
| health (anti-aircraft) | an anti-aircraft vehicle that is explosive or flammable, set to 14 % of its initial health by the campaign's own setter; the ORIGINAL `vehicle_critically_damaged` is then asked whether it is critical (strictly below 15 % in integer arithmetic) and the health is put back, and the case reported not eligible, if it is not; up to eight vehicles are tried in order and each is reported with its reason | none: the campaign's own update loop runs for 20 simulated seconds | an anti-aircraft vehicle's fire roll |
| health (person) | none changed: the original predicate is asked once and its answer recorded | none | a person's bleeding is SOURCE-UNREACHABLE: `vehicle_critically_damaged` returns FALSE for ENTITY_TYPE_PERSON before it looks at the health (`vehicle.c`), so no health reaches the roll; this is declared, the predicate is not edited to force it, and the run does not count it as missed by chance. A later extraction moves the eligibility to the host too, while the reference host preserves the original behaviour |

Where the weapon ends and with what kill code in a blast case stands in for the flight's decision, which the weapon-execution task owns; that is the test's declared precondition. The kinds, weapons and launchers are chosen by a rule written in the script (the first living entity; a weapon class some launcher really carries, found by the Task45 read-only query), never invented; a case that cannot be done (no living entity, no carrier, a refused launch) is recorded as not done.

**What the driver guarantees (checked against the real driver code over a stand-in entity list, `c-checks/case_checks.c`, 27 checks (32 after the refusal-as-data change below) under AddressSanitizer and UndefinedBehaviorSanitizer; NOT a native run):** a launcher whose existing launched-weapon children exceed the snapshot (256) is refused BEFORE the launch, because new weapons could not be told from old; a launch that creates more than 256 weapons retires every provably new weapon (the snapshot is complete, so exactly those) and returns an explicit error with the counts, never retiring an old weapon; a blast's resulting position (receiver position plus the offset, finite, on the game's own `point_inside_map_area`) is validated before anything is launched or mutated, so the default 5 m offset near the map edge is reported `placed=0` instead of reaching the weapon-position setter's engine stop; a vehicle's health is changed only where the original critical predicate accepts it. The previous driver (`450ecf60a`) run against the same checks fails 16 of them and aborts at the setter's engine stop (`checks/case-mutation-450-1.log`).

**How a case's deltas are keyed.** The report has indexed rows (an entity kind, a warhead, a kill code, a timed roll's kind, an unobserved kind). `lua/combat-counters.lua` (loaded by the witness and by the test, so the test runs the real code) keys each counter by every identifier its row carries, e.g. `cmb-blast-kill.code=3.calls`, `cmb-warhead.type=4.real`, `cmb-kind.type=ENTITY_TYPE_HELICOPTER.collisions`, `cmb-timed.kind=4.draws`, each holding that row's own value (never a sum over rows), so a change in one kill code is visible while a later kill code's row is unchanged. The first version keyed `cmb-blast-kill` without its code, so the later code's row overwrote the earlier one's and a changed counter disappeared from the delta; the test that exposes it (two kill-code rows, code 3 up and code 7 unchanged) failed on that code and passes on this one (`cargo-test-46-counters-red.log`, `-green.log`).

**What a case result means.** `done` in the witness output says only that the PRECONDITION was met (a receiver was found, a placement was on the map, a health was accepted by the original predicate). It is not a statement that a physical path ran. A path ran if and only if the case's `case_delta` row shows it (a collision on the kind, a capability draw, a blast call, a timed roll's draws and hits); a timed case also emits `timed_activity` with the draws and hits separately. Events the war logs between two cases are kept (scope `pre:<name>`), not discarded. The run summary's `preconditions_met` is not coverage. The natural-run audit does NOT judge the controlled file; a controlled acceptance will read the deltas and the eligible draws, never the process exit or `preconditions_met`.

**Declared limits of the witness:** no player entity exists in this boot, so the player-controlled target, the multiplayer multiplier and invulnerability stay unreached; a rocket destroyed by a blast needs a second, rocket-type victim weapon and is not in this first witness; the fixed-structure restore is D4 and stays observed-not-driven; the campaign consequences of a kill in a case (credit, speech, force notifications, losses) happen as the original does them and change the world for the cases after it, which is why the order of the cases is fixed in the script.

## Review of `871b51362` (two P2) and the corrections

Review of `871b51362` (the same reviewer, two P2) and the corrections. The review SUPPORTED the first `9d7cd106a` partial original run independently (39 cases, 79 trusted reports, contiguous event log, all 39 case hashes, raw size and SHA) and measured what it did, EXACTLY: the six high-explosive cases that launched wrote health; the twelve solid-shot cases delivered collisions and capability draws WITHOUT any health write; the six weaponless cases took the no-weapon exit; the anti-aircraft timed roll drew 201 times, hit 46 and killed 0. So the five previously unreached families (PERSON, PYLON, SCENIC, SITE, SITE_UPDATABLE) got collisions and capability draws, and a positive health write only where a high-explosive weapon was delivered; it is NOT claimed that all five received health writes. OBJECT had no living entity, and a person's bleeding is source-unreachable. The 13 rejections remain unaccepted, and ammunition exhaustion of the old run is INFERRED, not proven (the old raw diagnostic did not record the count). `871b51362` itself was never run natively.

1. **The plan is an ESTIMATE, and the caller follows the LIVE ammunition.** The static figure (3 x living kinds + 1) counts LAUNCH CALLS but a carrier's `weapon_count` is ROUNDS: the campaign's launch call fires a whole salvo for an AI launcher (`wn_creat.c launch_client_server_weapon`) and each weapon created spends its burst size of rounds (`weapon.c`), so one call can create several weapons and spend several rounds. No claim is made that a round count covers N calls: a count BELOW the figure cannot cover the plan (a necessary condition), and that is all the figure says (`estimated_shortfall` in the rows). (a) The class of a ROLE is chosen by `combat-plan.lua choose_class`: the first class in the script's preference order that is not estimated short, else the one with the most ammunition, and the `chosen_weapon_class` row keeps `count`, `planned`, `estimated_shortfall`, the `reason` (`preferred`, `first_affordable_alternate`, `none_affordable_most_ammunition`) and the preferred class: a dual-purpose carrier of six rounds no longer displaces an affordable plain high-explosive carrier. The roles are the script's own (high explosive: dual purpose, plain, anti-aircraft, anti-tank; solid or conventional) and are never widened. (b) Every launching case calls `pick`: a read-only query of the live count of each carrier of the role, the chosen one first, and the first whose count covers what its last launch cost (learned from the case rows' `ammo_before` - `ammo_after`, at least one) launches; a change of carrier is a `carrier_changed` row, and a role with no carrier left is a `case_skipped` row with a name, never a launch from something else or a case counted as found. The actual debit of each case stays in the row (`ammo_before`, `ammo_after`, `refused`), and found=1 is still not coverage. No private physics is mirrored. The tests run the REAL `combat-case.lua`, `combat-plan.lua`, `combat-report.lua` and `combat-counters.lua` against a small stand-in for the engine (inventory, launch cost, the refusal and report texts): with a six-round dual-purpose carrier and a hundred-round plain one the caller takes `he_plain` and makes no launch from the small carrier; with a launch costing four rounds and a ten-round dual-purpose carrier it launches twice, changes carrier once and is never refused. With the `871b51362` Lua the same tests FAIL by behaviour (ten launches on the six-round carrier, four refused; ten calls and eight refused in the salvo case), `checks/caller-red-871-2.log`; with the corrected Lua they pass (`checks/test-p46-all-1.log`).
2. **The case driver validates before it launches (`eech_cmb_case.c`).** The launch helper answers an unsupported launcher kind, an invalid weapon sub type and a dead launcher with the same nonzero status (`eech_wpn_fixture.c eech_wpn_case_launch_run`), so the driver can no longer treat every nonzero status as a refusal. Before the launch it asks the helper's read-only query (`eech_wpn_case_query_run`, which changes nothing): an unknown host id or unsupported launcher kind is an ERROR with the helper's reason (`launcher_cannot_be_used_for_a_case_launch`), a weapon sub type the helper does not know (`warhead=-1`) is an ERROR (`weapon_sub_type_not_valid`), and a launcher that is not alive is DATA (`refused=1 launch=case-refused|reason=launcher_not_alive`, nothing launched or changed), because the campaign does not launch from a dead launcher. ## Audit tool

`eech-campaign/tools/combat-trace-audit.py` (exit 0 pass and complete, 1 failure, 2 incomplete) and `combat-trace-audit-selftest.py <real complete trace> <run.json>`, which proves against that real file that the audit accepts it, rejects 43 single targeted corruptions or incomplete runs, and runs 17 bounded-reader and limit controls (63 cases).

* **It requires the report structure before it judges a value.** The emitter writes one report for boot, one for each checkpoint marker and one final report; each holds exactly one of nine singleton rows (`cmb-hash cmb-integrity cmb-capability cmb-damage cmb-explosion cmb-blast cmb-install cmb-repair cmb-log`) and exactly one `cmb-timed` row for each of kinds 1..6; the optional rows (`cmb-kind cmb-warhead cmb-blast-kill cmb-unobserved`) are unique by type or code; no other report row exists. The groups must match the boot configuration, the checkpoint markers (each marker before its own report, the boot report before the first marker) and the final clock, and a repeated group is two groups. A trace with rows removed or repeated fails; the previous audit (`450ecf60a`) returned exit 0 and PASS for traces with ALL damage rows removed or ALL checkpoint integrity rows removed (`audit-structure-red-green.txt`). The real original has every required row, so this was a checker defect, not a native failure.
* **It checks the emitter's ORDER.** After the boot report and its drained events, each checkpoint is a marker, the events drained at it (scope `log` only) and then its report; after the last checkpoint come the drained events, the unscoped `run` marker, DIRECTLY the final report, and then nothing. A `run` marker moved after its whole final report (no datum changed) returned exit 0 / PASS from the previous audit and now fails, as does a foreign row between a checkpoint marker and its report (`audit-order-limits-red-green.txt`); the real original passes unchanged.
* **An unfinished run is INCOMPLETE, never a pass.** An incomplete LAST report is tolerated only while there is no final `run` event and is then NOT_EVALUATED; a hole in any earlier report fails; a final report without its `run` event fails. The event tallies of a checkpoint report are checked against exactly the events drained at or before it.
* **It reads under its limits, and validates them first.** The shared reader refuses a line limit that is not an integer of at least 1 and a total limit that is not an integer of at least 0 BEFORE any read (a negative line limit used to become `readline(-1)`, an unbounded request); the instrumented file sees no request at all, for the reader called directly and for the command line. Every valid read asks for at most min(line limit, bytes left) + 1 bytes, so an oversized line or file is rejected before it is retained, decoded or parsed; it is never read whole (`--line-max`, `--max-bytes`). The self-test drives the REAL read path through an instrumented file and asserts that no request exceeds the bound, using a 2 MB unterminated line against a 1,000-byte limit; it does not allocate a huge input or measure memory.
* It declares the legacy typing of the original run's `cmb-kind` `blast` counter (above).
