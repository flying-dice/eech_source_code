## 1. What the original does (verified in source; unmeasured)

`get_local_entity_target_point (en, &point)` (`aphavoc/source/entity/en_misc/en_maths/en_maths.c:166`) answers four ways:

| branch | condition | result | writes |
|---|---|---|---|
| 1 | the entity has a 3D instance with a `TARGET_POINT` sub-object | the sub-object's world position | **overwrites `inst3d->vp` (position, then attitude) from the entity pose** before composing the world viewpoint |
| 2 | an instance without one | the entity position | none |
| 3 | no instance, `INT_TYPE_IDENTIFY_FIXED`, shape not `OBJECT_3D_INVALID_OBJECT_INDEX` | position, then `target_point_offsets[shape]`: **x and z only when the offset has a non-zero x or z AND the heading is non-zero** (rotated by the heading); `y` is always added | none |
| 4 | no instance and not a fixed object, or a fixed object with the invalid shape | the entity position | none |

**The heading-zero quirk is legacy behaviour and stays**: a fixed shape with a horizontal offset and a heading of exactly zero gets its `y` offset but not its x/z offsets. It is recorded and checked as a contract of the report, not corrected.

`target_point_offsets[]` is filled by `initialise_target_point_offsets` (`wn_dbase.c:6748`, called from `wn_funcs.c:105`): per model index, the world position of the model's `TARGET_POINT` sub-object, or, when it has none, the bounding-box
centre with `y = max (centre y, 0)`; the invalid index is zero. These offsets are **physical model-derived facts** and belong to the host under D3. The same function first calls `calculate_seeker_limits_from_launch_angle`, a separate campaign/weapon-policy
calculation that **stays Core, in its order, once per invocation of that function**; the function must not be moved as one piece, and the observer's census hook sits before that call and changes nothing about it.

## 2. The observer (`target-point-fixture`)

A test-only cargo feature (`eech-dc/target-point-fixture`), off in every shipping and every other fixture build, built by `tools/build-windows-target-point-fixture.sh` (the unchanged `build-windows.sh` with one added cargo argument, the same wrapper pattern as the
aim, route and other fixtures). It follows the route fixture's mechanism: hooks are **staged patches** (`TARGET_POINT_FIXTURE_PATCHES` TP1..TP20 in `build/patches.rs`, strict occurrence-count checked), applied only with the feature to the staged copies of
`en_maths.c`, `wn_dbase.c`, `weapon.c` and `wn_move.c`. **The in-tree sources are not edited**, so with the feature off the staged files are the shipping ones and no hook, definition or entry exists. Other files: `csrc/eech_tp_hooks.h`, `csrc/eech_tp_fixture.c`,
the three entries in `csrc/eech_engine.c` (appended after the existing text; the file's literal NUL byte is untouched) and `eech_engine.h`, `eech-engine-sys` externs, `Engine::target_point_summary / target_point_offsets / target_point_event`, the Lua methods of the same names, the driver
`lua/target-point-characterization.lua` and its local guards `tests/target_point_characterization.rs`.

What each hook does: it **adds a call and changes no original statement, argument, order or value**, does no floating-point arithmetic (floats are copied as bit patterns), draws no random number, reads no clock, keeps no pointer on the wire and writes no campaign or model byte.
The query hooks record: the caller (TP18/TP20) and its detail; the branch (TP3/TP4, and the no-instance default of 4 promoted to 3 by TP6 for a valid shape); the entity type; the host identity; the semantic model (the instance's scene, or the shape's, by compiled scene name); the shape; whether a horizontal
offset exists (TP7), the heading the original read (TP8) and whether the rotated offsets were added (TP9); the returned point (TP10); and the **instance viewpoint, position and attitude (twelve words), before and after**. The census hooks (TP12..TP16) record, per model index, which producer
branch filled the entry (sub-object, bounding box with its six bounds, or the invalid index's zero) and the offset bits; at report time each entry is compared with the live table, so a later write to it shows as `live=0`.

**Host identity is read, never allocated.** The fixture calls `campaign_object_host_id`, which returns the identity the host already issued (a structure's, or a rostered mobile's) and never asks the host. `campaign_object_identify`, which the aim path's `fill_host_id` uses and which *asks the host for
a structure's first identity*, is deliberately not used, so the observer cannot issue an identity as a side effect. `host_id_state` is `present` or `absent` (an object with none yet); the identity text is the last field of the line and may hold spaces. This helper validates the entity heap and, like the aim
path that calls it first, would stop the engine on an invalid entity; that is the only extra campaign function the fixture calls. It gives host-identity *availability* only; it does not decide an answer shape for a host query.

### Reports and the driver

Three read-only entries, bounded and refused rather than truncated: the **summary** (counters, a branch x caller matrix, the case counts, the census totals and two verdicts), the **census** (one row per model index), and **one recorded query** by index (capacity 4096; calls beyond it are counted as `dropped` and
make the capture not whole). The driver boots exactly like `campaign.lua`, reads the summary and census straight after the boot (the census must be whole before any frame runs), runs `seconds` (default 3.6) in `frame_ms` (default 100) frames, samples the summary at the requested cadence, reads the summary and
the census again, requires the census byte-equal, and reads every recorded query once. It **selects no target, creates no entity and calls the original from nowhere**: only queries the campaign's own update loop makes are reported.

Safeguards, each exercised by a local guard with the real driver: strict argument checking before any side effect and an exclusive output closed on every exit; the native grammar line by line and the summary's arithmetic (every begun call is exactly one of stored, dropped, abandoned or open); a verdict is believed only if
the counters say the same, both ways; the event rows must reproduce the summary's branch and caller matrix; a monotone counter, a clock that advances, and a census that does not change; a query of branch 3 must agree with its own offset and heading (`xz_applied` exactly when the heading is non-zero, `+0.0` and `-0.0` alike); a
branch 2 call must not change the instance viewpoint; sequence numbers strictly increase; an engine call that fails, a malformed report or a module without the feature (`NOT RUN`) stops the questions and is never a zero-success.

**No query reached is stated, not hidden**: a whole capture with no query passes with `natural_queries_reached=false`, `branches_reached=none`, an `unreached` row and a standard-error line; nothing is claimed covered.

## 4. Unproven and not covered

* **Nothing has run.** The C, the patches' anchors against a real staged tree, the Rust, the Lua driver and its guards are unbuilt and unrun here; static counts of every anchor in the four sources were checked (each occurs exactly once) and nothing else. The guards use C-shaped *synthetic* reports and prove the driver, not the observer.
* **Natural reach is unknown.** Which branches the 3.6 s controls reach, and whether any query is reached at all, is Root's first measurement. Branches 3 and 4 depend on targets having **no** 3D instance, which in a headless campaign is the common case far from any view, but that is unmeasured. Branch 1 and 2 need an instance.
* **Controlled coverage is not implemented.** If the natural runs leave a branch unreached, the options are an already established aim scenario (the D2 person-case pattern, `lua/aim-person-case.lua`) or a separately labelled controlled option that calls the original on a chosen entity. The second would *perturb the campaign* (branch 1 overwrites the instance viewpoint, which this observer
  deliberately does not restore) and would claim neither natural coverage nor restoration; it is not built, and no geometry is invented for it.
* **Downstream readers of the written viewpoint are not proven.** The sibling code in `weapon.c` (lines 1343, 2116, 2340, 2501, 2613, 2931) writes `inst3d->vp` from the entity pose (the same write branch 1 makes) at each of those sites, evidently so that the viewpoint reads that follow see the pose (whether every one of them is preceded by such a write was not checked), and `get_sub_object_relative_position` (`sub_anim.c`) subtracts the instance position from a world position, so it is
  base-independent; about 50 references to `get_3d_sub_object_world_viewpoint` exist in all (gunship avionics and cockpits, dynamics), and a reader of `inst3d->vp` that does not refresh it first has not been ruled out. The report records whether the write *changes* the words (`vp_changed`), which is the evidence that bears on it; a host answer that does not write the viewpoint is a semantic claim to be justified after that
  measurement, not assumed.
* **FPU and ordering.** No RNG is visible in the function. Whether the caller's FPU state or the update order matters needs the actual runs; the hooks run inside the engine entry under the same mode and add no arithmetic. The observer's call to `campaign_object_host_id` runs before the original body, outside its FPU use. TP8 takes the address of the local `heading` so the hook can copy its bits; on the x86-64 SSE single-precision target that can change code generation but not a value, and that is argued here, not shown for any other target.
* **Not observed**: the camera, HUD and player callers (counted only as unattributed), `gd_attck.c`'s direct table read, the population of `target_point_offsets[]` under the original model accessors (this feature composes with the host model profile that ships), and any lazily constructed model effect (the census records what the boot already computed; it constructs and measures no model).
* **No host answer shape is chosen, no extraction is made, and no baseline, tolerance, input, scenario, flag or oracle changed.** D3/Task 52 stay open until a real original characterization, an extraction, the actual authority and regression comparisons, review, current CI and normal delivery.

The driver now has a generic `checked_call` (the pcall, the `report_failed` row and the stop-after-engine-failure message) and `ask` is `checked_call` plus the string requirement, used only for the three text reports. The clock is read with `checked_call`, not stringified, and `check_clock` is unchanged. New guards: the table clock passes, a clock answered as text is malformed with no frame run, and a clock call that raises stops the questions and is reported together with a failed close.

**2. Exact protocol joins** (metadata, word and count equalities of what the observer emitted, not a recomputed physical answer; no C change):

The synthetic positives now carry them (they carried 3 before, which was not C-shaped).

* **The census.** Every later summary, a mid-run sample or the final one, must carry the boot's census totals (all eleven) and verdict; the final summary is also joined to the final raw rows (not only the rows to the boot rows). The query counters, which do grow, are not part of this.

The guards' fixtures are faithful first (census-derived offsets, a shape with no horizontal offset, real aim details), and each join has a single-fault damaged form that cannot pass without it; the earlier assertions and predicates are kept. ## 6. The first native actuals at `d1ba9e71b` and the per-pass census (source only; UNBUILT, UNRUN, UNREVIEWED)

**What actually happened.** At `d1ba9e71bc4e311f719b3e9391fc19f6eacb2ce6` (and the lint-only `deefe75db`: fmt and BOTH strict exit 0 at 18:28:21) the default and feature packages passed with all 20 driver guards each and the Windows fixture built. The first native run on fresh Georgia and Lebanon roots then **failed in both**: native and controller exit 1 at 18:28:40-42, the four full retail pre/post input checks exit 0, all 84 payloads unchanged, and the driver refused `NOT MEASURED: offset census not whole (runs 2, recorded 3026 of 3026)`. The summary also counted **one query already made during the boot** (branch 1, unattributed, `vp_changed` 1), so "zero calls" would be false; the driver refused before draining events, so that query's rows and the frames were never read. The two roots are consumed. No row of these captures is accepted, the earlier source histories (`73f245be5`, the Docker interruption, the lint) stay as they are, and the failure is not recast.

**The assumption that was wrong.** The census had one table and a once-only completeness rule. `initialise_target_point_offsets` is reached **twice in one public boot**: `eech_engine.c:247 push_ui_screen (init_screen)` -> `init_sc.c:227 full_initialise_game` -> `init.c:935/937 initialise_entity_system` -> `en_init.c:87 initialise_entity_functions` -> `en_funcs.c:189 overload_weapon_functions` -> `wn_funcs.c:105`; then `eech_engine.c:311 reinitialise_entity_system` -> `en_init.c:112` -> the same chain. The second pass counted as 3026 duplicates and overwrote the first pass's words, so the first pass's values are **unavailable** in the failed captures; they are not claimed equal to the second. Each pass runs `calculate_seeker_limits_from_launch_angle` once before its geometry loop, so this boot observes the campaign weapon-policy calculation **twice** (once per pass); the earlier prose that it ran once per boot was an unmeasured assumption. The policy stays Core, in its order, unchanged and not deduplicated.

**The correction (observer, plumbing, driver and guards; no C original statement, anchor, value or order changed, and the engine file's NUL is untouched).**
* The census is a bounded history of **generations**, one per invocation of the initialiser (capacity 4, `TP_GENERATIONS`), each with its own ordinal, ended/interrupted state, row cohort and counters for duplicates inside the pass and indices outside the table. A pass beyond the history, a pass abandoned by the next begin, a hook outside a pass and a pass left open are counted and make the census not whole. No pass count (not even two) is part of acceptance.
* A pass is a **complete snapshot** if it ended, was not abandoned and recorded every index exactly once with the invalid zero once. Whether it still equals the **current** table is a separate fact (`live_mismatch`): an older pass may differ, which is a fact about it and not a lost capture. The census is whole only if every kept pass is a complete snapshot and the **latest** pass is the one the table holds now.
* `target_point_offsets (generation)` reports one pass's rows (the Rust bound is `TARGET_POINT_GENERATIONS_MAX`, checked before and by the engine). The summary carries a `tp-census` line and one `tp-pass` line per kept pass. Each query records the latest ended generation when it ran (`gen`, -1 for none yet) and whether a pass was running (`gen_open`); the one boot query and the caller, detail, case, identity and viewpoint evidence persist across the passes.
* The driver reads and keeps **every** pass in full right after the boot, **before** the verdict is judged (a capture that is not whole still retains what it saw), and again at the end. Each pass is joined to its own summary line; every pass the boot held must appear unchanged in every later summary (a later pass is a new original product, judged by its own line and the final verdict; an older pass's live facts may change only once a pass was added); the words of an older pass must be unchanged at the end, byte for byte when no pass was added. A fixed-shape query's offset words and model name are joined to that shape's row **in the pass that was the latest to end when the query ran**, never to a later pass, and queries may not name an older pass than the one before them. The previous predicates (clock table, caller/detail pairs, all seven case totals with partial bounds, host identities, viewpoints) are kept.

New guards use C-shaped synthetic history: two passes with different old and final words for two models, a query between passes bound to the older pass, a later third pass whose own line and rows are judged separately, and single-fault forms (a pass line disagreeing with its rows or the boot, a lost pass, a live fact changed with no pass added, a duplicate inside a pass, a latest pass the table no longer holds, a query naming a pass that is not held, none, one still running, an older pass than its predecessor, or the other pass's words). They prove the driver, not the native observer. Still unproven: that this compiles or passes, what a corrected native boot reports (including the content of the one boot query), whether any pass beyond the second occurs, the FPU, ordering and viewpoint-reader limits of section 4, and any natural query coverage. No production query, extraction, ABI or host answer shape is made.

**Sampled call boundaries (source only; UNBUILT, UNRUN, UNREVIEWED).** The independent review found that a query's `gen` was joined only to the final ended passes and to the monotone order of the events, not to the moments the driver actually knows the observer's state. The observer assigns a query's `seq` from the call count when it BEGINS and captures the latest ended generation (and the open flag) then. So against every summary the driver reads (the boot, each sampled frame, the end), with that summary's call count and latest ended pass: a query that began before that call count cannot name a later pass than the summary's, and one that began at or after it cannot name an earlier one. Nothing is assumed between samples, the open flag (unknown at the query's moment) is not constrained, no pass count is forced, and the latest ended pass may not go backwards between samples. A boot query between the two initialiser passes (an earlier pass, with a pass possibly running) and a later query after a third pass remain valid; a coherent-word substitution that names a pass added only after a pre-boot query, or one older than the latest that had ended before a post-sample query, is malformed. The guards add a coherent positive with a boot query between passes, a pass added between samples and a sampled boundary, and single-fault substitutions of the future pre-boot generation, the stale post-sample generation and the stale post-boot generation (each asserted to really change its report).

## 7. After the real `7af39eca7` characterization: the controlled probe for the unreached cases (source only; UNBUILT, UNRUN, UNREVIEWED)

**What the real 7af captures established.** At `7af39eca73` both scenarios ran native and controller 0 with the four pre/post input manifests 0 and all 84 payloads unchanged: each boot runs two legitimate initialiser passes of 3026 rows (587 sub-object, 2438 bounding-box, 1 invalid zero; 522093 B of raw text each at the boot and at the end), Georgia reached one boot query (branch 1, generation 1, instance viewpoint changed), Lebanon 217 (1 boot and 216 `aim_vectors`, all branch 1, generation 1, three viewpoint changes in all). **Source-backed choice.** The natural witness will not reach the other cases by waiting, so a bounded controlled option is added, following the `aim_lead_probe` precedent (the campaign's own function called once on real live entities through the engine entry, reported as a probe, never as natural coverage). Source inspection found: the aircraft and vehicle families (and weapons and smoke lists, which are not probed) answer `PTR_TYPE_INSTANCE_3D_OBJECT` and the default for any other type is NULL, the structures answer `INT_TYPE_IDENTIFY_FIXED` and `INT_TYPE_OBJECT_3D_SHAPE`, and the census (587 sub-object, 2438 bounding-box models) says which models have a `TARGET_POINT`, so an entity with an instance of a bounding-box model is a real candidate for branch 2 and an instance-less structure for branch 3. The probe therefore walks the live entity list **once**, over the families a target can be (anti-aircraft, fixed wing, helicopter, person, routed vehicle, ship, and `campaign_object_is_structure` types), classifies each entity using only reads the original makes (no floating-point arithmetic: a float is zero if its magnitude bits are), keeps the first two per case in list order, and calls the ORIGINAL once per pick as the controlled caller. The cases are: 1 an instance without `TARGET_POINT` (branch 2); 2, 3 and 4 a fixed object of a valid shape with no horizontal offset, with a horizontal offset and a non-zero heading (rotated), and with one and a zero heading (the legacy quirk, kept); 5 no instance and not fixed; 6 a fixed object with the invalid shape (branch 4). Branch 1 is not repeated.

**Preconditions, writes and limits.** The probe is one-shot, refused while a query or a census pass runs, and runs after the boot census is whole and before any frame. Branches 2 to 4 write nothing (only branch 1 writes the instance viewpoint, and it is not probed), so there is nothing to set or restore, and no restoration is claimed. It issues no host identity (a structure's identity is read, absent if the host never issued one). The entity is chosen by the fixture, so these queries are not campaign target selection, not aim or weapon coverage, and not natural evidence; they are recorded as caller class `controlled_probe` (the case as its detail), counted in their own row, and kept out of `queries`, `branches_reached` and `natural_queries_reached`, which stay the natural run's. The driver checks that each controlled query took exactly the case it was picked for (the selector's reads must agree with the original's), that the controlled queries are exactly the probe's picks, and that no controlled query exists unless `probe=controlled` was asked. **A case with no live candidate is UNAVAILABLE**: it is reported (`controlled_unavailable`, a `probe_unavailable` row, the standard error) and never counted as success; the minimum setup that would supply it (for instance a structure with a heading of exactly zero, or a mobile with no instance) is a fixture-set state write and is deliberately not done here. Words, identities and side effects are whatever the original produced; no value is recomputed. Whether any case has a candidate in the retail campaigns is unmeasured until Root runs it. Guards use C-shaped synthetic reports and prove the driver, not the observer. Whole D3 and Task 52 stay open: the host query extraction, authority and refusal, deterministic regression, review and delivery are all ahead.

**Probe scan safety and accounting (source only; UNBUILT, UNRUN, UNREVIEWED).** The independent review of the controlled batch found the scan unbounded and its early `break` indistinguishable from a complete scan. The probe now visits at most as many list nodes as the entity heap has slots, validates every node as an aligned slot of that heap by integer address BEFORE reading its type or successor (never comparing unrelated pointers), and treats anything else as an INCOMPLETE scan: it is refused (`tp-probe-refused reason=list_longer_than_heap | list_node_not_a_heap_slot`), nothing is called, no case is ever reported unavailable from a partial scan, and the once flag is untouched. The report is staged first (its size depends on the scan alone) and a buffer that cannot hold it refuses (`report_capacity`) before anything is consumed; the once flag is taken only after a complete scan and a fitting report, and immediately before the at-most-two original calls per case. A refusal reaches the driver as the engine's bad-argument error carrying its reason, which stops the run with no frame and no query read. The report now says `status=complete visited=<list nodes> entities=<considered families>`; the driver requires `sum (candidates) + shape_out_of_range <= entities <= visited`, so a report with picks but no population is malformed, and binds the controlled queries to the exact contiguous span of call numbers that starts at the boot sample's call count and is as long as the picks (the probe runs once, immediately after the boot sample and before any frame): no controlled query outside it, no natural query inside it, and the natural counts cannot go negative. The earlier drift guard compared the emitter's `site_name` returns in source order with the driver's class table; the protocol is the class NUMBER, and the guard now maps each enum class to its `case` name (or the `default`) and compares by number, plus the class count and the controlled class index.

The reviewer's last note on the scan: a valid aligned heap slot and an eligible type do not establish the entity data that the typed pointer, int and float getters dereference. An eligible node is now required to carry non-null live data (`get_local_entity_data`, the campaign's own accessor) BEFORE `probe_bucket` or any typed getter runs; a node without it refuses the probe (`tp-probe-refused reason=eligible_node_without_entity_data`), like every other incomplete scan: nothing is called, it is not skipped, and it is never counted as an unavailable case. The pointer, alignment, visit bound, report preflight and once-flag semantics are unchanged; the source-contract guard orders the new check after the type and before the first typed getter. ## 8. The setup probe for the three cases with no live candidate (source only; UNBUILT, UNRUN, UNREVIEWED)

**What the measured controlled run established** (`c500a314a7`, Root's report; not re-read here): both scenarios completed valid cohort scans (Georgia 63526 list nodes, 39973 eligible; Lebanon 91096, 64580; none outside the table) and the read-only probe called the original for cases 2 (fixed, no horizontal offset), 3 (rotated) and 4 (zero-heading quirk), two picks each, with the instance viewpoint unchanged. Cases 1 (an instance without a `TARGET_POINT`), 5 (no instance, not fixed) and 6 (a fixed object with the invalid shape) have **no live candidate** and are UNAVAILABLE. The read-only mode and its measured results are not changed.

**Source analysis of the obstacle.** There is no typed setter for `PTR_TYPE_INSTANCE_3D_OBJECT`: the aircraft and vehicle `set_local_ptr_value` handle only the sound effect and the registration lists only that type, so the typed API cannot give a mobile another instance or none. The field the typed getter reads (`aircraft`/`vehicle` `inst3d`) can be written directly, which is a fixture-only use of a private layout that never reaches the wire. There IS a typed setter for the shape of a fixed object (`INT_TYPE_OBJECT_3D_SHAPE`, a plain field assignment in `fx_int.c`). `construct_3d_object` adds to `current_number_of_3d_objects_constructed`, `current_amount_of_3d_objects_memory` and `object_3d_scenes_creation_count[scene]` (all symmetric in `destruct_3d_object` and all readable), allocates the instance, its sub-instances and texture-animation array, and calls `skin_random`, which draws `rand()` only for a scene that has a skin; the default pointer getter for every other entity type is NULL, and the default int getter for `INT_TYPE_IDENTIFY_FIXED` is 0, so a mobile whose pointer is NULL takes branch 4 not-fixed.

**The mode (`probe=setup`; separate, opt-in, exclusive with `probe=controlled`).** Once, after the boot census and before any frame, with the same bounded and validated list scan as the read-only probe (aligned heap slots, a visit bound, live data before any typed getter, refusal on an incomplete scan), it picks real live entities and gives each case a declared physical PRECONDITION, calls the ORIGINAL once, restores it and verifies the restoration before the next case: (1) a real aircraft or vehicle with an instance has that pointer replaced by a temporarily constructed instance of a real census bounding-box scene that has no skin (so nothing is drawn from `rand()`; a fresh instance is also checked to have no `TARGET_POINT`), then restored and the temporary instance destructed; (2) the instance pointer of a real mobile (possibly another one than case 1's, and fewer than three entities may be involved when the cohort is small) set to NULL, then restored; (3) a real fixed structure's shape set to the invalid index by its typed setter, then restored. Each change is verified through the typed getters, the real instance's viewpoint words and, for the constructed instance, the three construction counters are compared before and after, and any failed restoration refuses with `restoration_mismatch_case_N` (the one refusal channel), stops the run before any frame, and is never recast. The allocator's internal state is not claimed identical, only those counters and the fields named. No pose is changed, so nothing leaks into later frames, and the procedure is bounded to three cases on at most three entities. Restoration is claimed only on a NORMAL return: the engine's fatal unwind (a `debug_fatal` anywhere between a change and its restoration, in the original included) has no guaranteed cleanup and no next frame, and nothing is claimed restored when the original does not return; the source checks of the normal path (pointer, shape, viewpoint words, counters) stand as they are. A case with no real candidate (no mobile with an instance, no bounding-box scene without a skin, no fixed structure with a valid shape) or whose precondition does not apply is NOT called and says why; nothing is invented. The temporary instance is an environment precondition, not migration or host authority; the queries are caller class `setup_probe` (counted apart from the natural and the read-only ones), never target selection or aim/weapon coverage. The driver checks each query is the case it was set up as, that its entity family and host-identity state are the changed entity's, that case 1 saw exactly the census bounding-box scene it was set up with (name included), that case 3 read the invalid shape, and that the setup queries are the contiguous span after the boot sample. The Lua guards use C-shaped synthetic reports and prove the driver, not the observer.

**Coupling that stays open.** `aphavoc/source/entity/special/guide/gd_attck.c`, `calculate_attack_guide_intercept_point`, reads all three local offset coordinates of `target_point_offsets` (lines 172 to 174) directly. It is an unmeasured consumer that a later host offset fact must also serve, and it is required Task 52 work (not deferred to D5); its guidance and selection policy do not move here. No production extraction happens before this fallback characterization, and whole D3 and Task 52 stay open.

**Setup report joins, corrected (source only; UNBUILT, UNRUN, UNREVIEWED).** The same reviewer found the setup report's join incomplete after the `03b` actuals (no separate C lifetime or RNG group). The driver now requires, for an available case, that `applied` and `called` are one fact (`called` needs `applied` and the reason `-`; a case not called has the reasons its own case can have: `scene_has_target_point` or `setup_not_applied` for case 1, `setup_not_applied` for cases 2 and 3), and for an unavailable case a missing-candidate reason that belongs to THAT case (`no_mobile_with_instance`, `no_census_pass` or `no_bbox_scene_without_skin` for case 1; `no_mobile_with_instance` for case 2; `no_fixed_structure_with_valid_shape` for case 3) and no names. The original model's index and name are joined to the census rows of the pass that was the latest to end at the boot, the constructed scene (case 1) must be a bounding-box model of it under its census name, and the sentinels (`to=-1` for the no-instance case, `to=0` for the invalid shape) have no name. Case 1's query is joined to the rows of the pass its own `gen` names (the pass that applied when it ran), not to whatever pass came last, so a later pass that says otherwise of the same model, arriving during the frames, neither fails a valid witness nor excuses a query that claims the later pass. The guards add the coherent positives first (a later pass whose rows differ, and each case-specific reason on the case it belongs to) and single faults for each join.

**Setup cases share one scan (source only; UNBUILT, UNRUN, UNREVIEWED).** Cases 1 and 2 are derived from the same scan of the same mobiles, and case 3 from a fixed structure, which is a different entity. The driver now requires that the setup's reported entity count covers one mobile (when case 2 is available) plus one structure (when case 3 is available), and no more, because cases 1 and 2 may use the same mobile; that case 1's "no mobile" reason holds exactly when case 2 is unavailable (an available case 1, or one short of a scene, needs the mobile case 2 has); and that a population of zero cannot carry an available or called case. All source-possible states stay valid: case 1 short of a scene (`no_bbox_scene_without_skin` or `no_census_pass`) with a real case 2, and case 1 available but not called (`scene_has_target_point` or `setup_not_applied`).

## 9. The first host geometry parity kernel (source only; UNBUILT, UNRUN, UNREVIEWED, no Core cutover)

**What moved, and where.** The numeric half of the target point now exists in the reference host's own store, `eech-world`'s `ModelStore` with `csrc/model_step.c`, next to the route and collision kernels it already holds. Nothing in Core, the public native module or the ordinary Lua path changed, and no Core table or hierarchy pointer is exported.

* `target_point_local(scene)`: the value `initialise_target_point_offsets` stores in `target_point_offsets[scene]`. Scene 0 is the invalid scene's zero. A scene with a `TARGET_POINT` record gets the world position of that sub-object under an identity pose (main object at the origin, identity attitude, scale 1), as the original does with a freshly constructed instance. Any other loaded scene gets its bounding-box centre, `(xmin+xmax)*0.5`, `max((ymin+ymax)*0.5, 0.0)`, `(zmin+zmax)*0.5`, with the double `0.5` and `0.0` of the original. A scene no file defined is still an in-domain slot the original constructs (zero bounds, no sub-objects): its offset is the zero bounding box (source `bbox`) and its world answer is `NoTargetPoint`, which is not the invalid scene's zero and not a refusal. An index outside the catalogue is an argument error, and a store that only inventoried the custom files (`load_inventory`) refuses with `custom_definitions_not_loaded`; a missing or corrupt required installation file is still a load failure. The bounding box is the SCENE box the store computes (`3dsubobj.c` starts it from a zeroed box, so it always includes the origin), not the main object's own box.
* `target_point_world(scene, position, attitude, scale)`: the instance branch of `get_local_entity_target_point` (branch 1), for a semantic root pose (position, nine row-major attitude words, relative scale; float bit patterns, no legacy structure or pointer). `NoTargetPoint` is the original's second branch.
* The kernel entries are `eech_model_target_point_bbox` and `eech_model_world_viewpoint`: the original's chain loop expression for expression (`position += R*(keyframe position * scale)` with the original's row-vector `multiply_matrix3x3_vec3d`, `scale *= keyframe scale`, `attitude = sub_attitude * attitude` with `get_3d_transformation_matrix(heading, -pitch, -roll)`), under the same guard as the other kernels (x87/SSE masks required, round toward zero for the call, the caller's state restored and verified on every exit). Which sub-object is meant is the store's existing first-match search (`route_node_index`, shared with the route lookups): the scene's own records, then each top-level sub-object's own records before its children.

**The hypothesis, labelled as one.** The world answer is for the state `keyframe0`: every sub-object at keyframe 0 and a relative scale the caller states (1 for a fresh instance), which is what `construct_3d_sub_objects` gives a fresh instance. A live entity whose sub-objects the campaign or the render path has since turned, animated or scaled is NOT covered, because the host does not hold that state. Nothing defaults it into success: the Lua `compare_target_points` replays every recorded branch-1 query (model, the recorded `vp_after` root pose, the recorded result) with relative scale 1 and lists the first mismatches, and a mismatch there is the missing fact to find before any live pose is accepted. Whether the main object's relative scale is always 1 in the recorded queries is the same kind of unmeasured input (the observer records the viewpoint, not the scale).

**The host Lua diagnostic path (not the ordinary path).** `store:scene_index(name)`, `store:target_point_local(scene)`, `store:target_point_world(scene, { position, attitude, scale? })` (0x-prefixed hex words) and `store:compare_target_points(path)`. The comparison reads the retained observer report (JSON Lines: the `offsets` and `query` events) and, for every pass and every `tp-offset` row the original recorded, compares the host's offset bit for bit and its source (`sub_object` / `bbox` / `invalid_zero`), and for `bbox` rows also the bounds the original centred against the bounds the host holds, so that a differing row says whether the input or the arithmetic differs. Rows the original did not record (`state=none`) are counted and not compared. There is no model-per-function mock oracle: the unit tests use literal expectations over tiny files in the original's formats, and the retail answer is Root's comparison, not these tests.

**Constructor RNG audit (source reading only; nothing measured).** `construct_3d_object` ends with `skin_random(object)` (`3dobjdb.c`, defined in `3dobjid.c`), which returns at once when the scene's `skin.animation < 0` and otherwise calls `rand()` exactly once (`rand() % number_of_textures`, or `rand() % texture` when the season has skins), whatever the season. `initialise_target_point_offsets` constructs one instance per scene per pass and runs twice per boot, so the C library's `rand()` stream advances once per skinned scene per pass before any later consumer. What the data and source prove: the count is data dependent (the number of scenes with a skin animation, which the host store does not read today). What is NOT proved and stays unmeasured: how many skinned scenes the retail data holds, whether a later consumer of `rand()` depends on the position in the stream, and whether a `srand` falls between the draws and that consumer. No constructor work is left to Core and none is invented in the host: a cutover must either reproduce the draw count or show, from a measured stream, that no consumer observes it. No baseline or tolerance was changed.

**What stays open.** The seeker limit calculation stays once per initialiser pass in Core. `gd_attck.c` `calculate_attack_guide_intercept_point` (lines 172 to 174) still reads all three local offset coordinates and stays a required consumer whose policy is not moved. No Core query is routed to the new methods and the public native ABI is unchanged. Not yet shown: bitwise parity on the 3026 retail rows of both passes and on the recorded branch-1 queries (Root's run), the live-pose state above, the `bbox` bounds equality on retail data, and the draw stream. The unit tests (13, including the host Lua face and the empty-slot guard) pass on the working tree in the pinned Linux image against hand-computed exact values over tiny fixtures; that is not retail parity.

**First retail comparison of the host kernel and the empty-slot correction (2 November 2026).** Root's read-only `host.model_store` comparer (no `eech_dc`, no campaign boot) ran on the ordinary Windows build of `83df5b871` against the retained Georgia and Lebanon captures: all inputs and payloads unchanged, 12104 offset rows compared per map (4 events of 3026: 2348 `TARGET_POINT`, 9752 `bbox`, 4 `invalid_zero`), and all recorded branch-1 queries (Georgia 1, Lebanon 217) exact under the declared `keyframe0` / main scale 1. Each map still reported `offset_mismatches` 1504, a count of conditions per event and not of unique rows, and that old result is preserved as a failure. The listed first causes were scenes whose original rows are genuine empty slots (bounding box and offset all `00000000`, for example scene 2762 `OLD_LAST` and 2832 `US_LIGHT_FIRING_POINT_DESTROYED`): the original constructs every in-domain scene, so these are the zero bounding box, but the host answered `scene_not_loaded` and the comparer additionally required the scene to be `loaded`. The reviewer confirmed this one empty-slot semantic group. The source change is only that group: an in-domain slot no file defined now gives the zero `bbox` offset and `NoTargetPoint`, `view.loaded` stays honest in the metadata, and the comparer compares the bounds without requiring `loaded`. The arithmetic, the floating-point guard and the first-match search are unchanged. The capped list does not prove all 1504 conditions have this cause, so the corrected source must be re-run by Root on a clean binary before any parity claim; this is not that run.
