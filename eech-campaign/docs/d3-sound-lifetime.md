## What the source says (read, not measured)

* `ss_updt.c`, the hosted `create_lightning_effects` (active) and the legacy `update_lightning_effect` (`#else`) create two sound entities per lightning expiry through
  `create_client_server_sound_effect_entity` (the lightning sample, then the thunder sample), each with a pitch of `0.85 + 0.3 * frand1 ()` drawn **between** the creations: the draw order and the entity
  allocation order are part of what must be preserved. The observer already brackets each creation with `ENV_FX_SOUND_BEGIN` / `ENV_FX_SOUND_END` (the next free entity indices before and after).
* `soundeff.c`: every creator passes through `create_local_sound_effect_entity` (the real constructor). It creates the entity, links it into the parent's special-effect list and, when the effect is valid, the
  update list, and `set_local_sound_effect_sample_indices` gives it `effect_lifetime = sum(size / rate)` over its samples, clamped to 40 s (300 s for music).
* `se_updt.c`: the SERVER routine takes `get_delta_time ()` (the global `system_delta_time`) off a valid, non-looping effect each update; below zero it kills the entity when there is no playback handle or the
  handle is not playing, and leaves it alone while the handle is playing. The CLIENT routine takes the same delta, clamps the lifetime at zero and never kills; an invalid effect is unlinked from the update
  list and its handle destroyed after `valid_effect_lifetime` runs out.
* The playback handle (`sound_effect_data`) comes from `play_local_sound` (`se_snd.c`) through `create_single_system_sound_effect`, which returns NULL while `sound_system_initialised` is false. The headless
  frame never calls the play path. Whether the headless build initialises the sound system at all (it is enabled only when the command line does not say no-sound and the process is not a dedicated server) is
  **not known**; the probe prints the flags as facts.
* `application_sound_effects[]` supplies `rate`, `size` and `original_rate` per sample (`snd_data.c`; `size` from the retail `audio/sound.hdr` when present). A full retail boot may therefore load real data; do not
  assume it does not (the earlier texture-model assumption was wrong in exactly this way).
* The wind, rain and terrain ambient children that consume sound are the ambient routine already characterised (groups 11 and 12); this probe does not touch them.

## Host-owned sound lifetime (candidate; source prepared 31 October 2026; UNBUILT natively, UNRUN, UNREVIEWED)

**What moved.** The ORIGINAL physical decisions that the finite original characterization measured (the seven controlled-data cases 4 to 10 of the original native 116ffd5fb with drivers 2a/d4, plus the zero-size natural run and
the three primitive controls) are now the HOST's, through two operations of the existing public environment provider (host-owned Lua -> `eech_dc` -> the campaign -> the provider callback; `ss_hostenv.h`):

* `sound_lifetime_init` (`soundeff.c set_local_sound_effect_sample_indices`): the sum of the samples' durations (`size / rate` per sample, a rate that is not positive adds nothing), the 40 s cap or the 300 s MUSIC cap, and 0 for a looping effect.
* `sound_lifetime_update` (`se_updt.c update_server` and `update_client`): the aging of a valid timed effect by the frame delta; the server's expiry and its decision (kill when there is no handle or the handle is not playing; leave a playing one);
  the client's clamp at zero (it never kills); and the countdown of an invalid effect's valid lifetime, then its unlink on the NEXT update with the release of any handle. The host asks `need_playing` (nothing changed) once, only for a
  server's expired valid effect that holds a handle; the campaign answers from its sound system.

The reference host (`eech-world/csrc/env_ref.c`, `src/env.rs`) runs the original C expressions as kernels (same types and expression order, the engine's own `max`/`min`) in the canonical arithmetic environment, on staged copies
committed only after the caller's floating-point state has been restored and read back. The host keeps NO state: the effect's stored fields stay in the campaign's record and travel by value (request: the descriptors' rate and size,
or the delta, validity, looping flag, lifetime, valid lifetime and whether a handle is held; reply: the new lifetimes, whether a valid effect's lifetime went below zero, and the decision).

**What the campaign still does, and why.** It reads each sample's rate and size from the sound database (`application_sound_effects[]`, loaded from the retail `sound.hdr`) and hands them over by value: this retained metadata input is a DATA
WORKAROUND, not host ownership of the sound database or of asset lookup, and it needs the host to own that metadata before the sound domain is really host-owned. It owns the record (the pause and resume functions, the network
pack and unpack and the observer read and write the lifetimes, so a host-held copy would diverge), the playback handle and the device (`get_system_sound_effect_playing`, `destroy_system_sound_effect`), and it APPLIES the checked answer in the
original order: both lifetimes are written, then the entity is killed (`kill_client_server_entity`) or unlinked (`delete_local_entity_from_parents_child_list`) and its handle released. The probe points (`ENV_FXE_*`) keep their original
places, so the same raw scenarios compare. Entity ids, allocation and list plumbing never cross the boundary. The campaign checks the whole answer before writing anything (finite numbers; a lifetime changes only for a valid timed effect, a valid
lifetime only for an invalid one; an expiry belongs to a valid effect, a kill to the server's expired effect, an unlink to an invalid one; a looping effect's constructor lifetime is +0) and stops with an error naming the provider on a missing
provider, a refusal or a malformed answer; there is no campaign arithmetic to fall back to in the hosted build (the original follows in the `#else`, for the original game's build only).

**Not moved, and still explicit (nothing here is a quiet deferral of D3):** `pause_local_entity_sound_type` / `resume_local_entity_sound_type` (the validity change and the update-list relink, separately from the device-bound play call; 40 compiled files

the speech cases of the constructor. The diagnostics the original logged in the constructor (a rate that is not positive, a sum at the cap) are not carried. A sequence of more than 16 samples is refused, not truncated (the sound
manager's own limit is 15).

**Cost.** Every call of a sound effect's update routine is now one provider request (including loops). That is the price of moving the decision and is to be measured, not assumed small.

**Conformance and witness.** The scenario entrypoints are the existing ones: the controlled-data cases 4 to 10 (`env-sound-lifetime.lua`) and the natural run must reproduce the finite original measurements on a NEW candidate native

## Original pause/resume characterization (source prepared 31 October 2026; characterization only; UNBUILT natively, UNRUN, UNREVIEWED)

**Scope and baseline.** The baseline is named exactly: the e502 / current hosted field-and-lifetime state with the ORIGINAL, untouched `pause_local_entity_sound_type` (`soundeff.c:97`) and `resume_local_entity_sound_type` (`soundeff.c:145`). It is not a wholly original
DLL: the lifetime decisions of the entities these routines act on are the host's (e502), and only the pause and resume routines are the original C. Nothing in production code, the host-lifetime kernels or protocol, the asset metadata or the backend changed, and no accepted case ID
(0 to 10) or old control was altered. This batch adds test-only observer-feature fixture cases 11 to 14 (`env_snd_pause_case` in `eech_env_fixture.c`) and their driver branch (`env-sound-lifetime.lua`). A new fixture C means a NEW native must be built before anything is measured.

**What the source says (read).** Pause sets `valid` to FALSE and `valid_effect_lifetime` to the delay only for a VALID sound child of the parent whose sub type matches, and returns the count it changed. Resume, for an INVALID matching child, sets `valid` TRUE, calls
`play_local_entity_sound` on the parent, inserts the child into the update list if it is absent, and returns the count. The session parent's play call is `default_play_entity_sound` (`en_snd.c`), a no-op (the session has no overload), so the validity change and the relink are
measurable without a device or a handle. Unrelated sound children of the session (the campaign's boot builds ambient ones) are left alone by a different sub type and are legitimately present in the totals.

**The cases (each builds its own small cohort of real sound entities, preflights every allocation, and calls the real routines in a printed order):**

| case | label | what it observes |
|---|---|---|
| 11 | `pause_then_resume_while_still_linked` | one effect: pause, then resume before any update has unlinked it: validity, return counts, list membership before and after |
| 12 | `resume_after_the_unlink_and_updates_after` | one effect: pause, three server updates (the countdown and the unlink), resume after the unlink (the relink), one more update |
| 13 | `repeated_and_no_op_pause_and_resume_counts` | resume before any pause (no-op), pause twice with different delays, resume twice: the return counts of repeated and no-op calls |
| 14 | `subtype_isolation_and_every_match` | three effects of two sub types (two of one, one of another): a pause of a sub type nobody holds, a pause of the one held by two, a resume of the other, a resume of the first |

Each step row (`env-sound-step`) records the call, the sub type, the delay word (taken with `memcpy`), the real return count and the number of updates made. Each scan row (`env-sound-scan`, before and after every step) counts, over the whole entity table (bounded by
`number_of_entities`, with a `complete` flag, never truncated): sound children in total, of the sub type, valid, invalid and linked in the update list. State rows capture the entity words by value. The driver joins these observations to one another (return count to cohort flips,
membership to the steps, state rows to the probe's CREATED and ENTER records) and computes NO delay, countdown or relink value. A difference is a reported observation, a malformed or self-contradicting report is a witness failure, a fixture refusal is a refusal, and an engine stop is an `engine_failure`.

**Restoration, stated honestly.** The end row restores the sound descriptor (rate and size), the delta and the tracking, and says `entity_state_restored=0 process_isolated=required`: the effects stay as the original routines left them, so each case must run in its own process, and the
report is not full state restoration. No call is made through a freed entity: the cohort is not freed before the last observation, and a server update is made only while the effect is live, a sound effect and in the update list.

**Not covered (printed as `env-snd-unsupported`, never a pass):** a resume on a parent other than the session (the range calculation and the per-family playback function); the playing and idle handles after expiry (they need the sound system's device); the independent destroy and network paths;
per-vehicle amplitude and pitch; any audible or player-side delivery. The follow-ups are controls on an aircraft or vehicle parent with a device. These cases do NOT move pause or resume into the host; that waits for the measurement, the comparison and an independent review.
