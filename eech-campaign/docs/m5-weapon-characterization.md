# D2: characterisation of the original physical weapon-execution code (EEDCS-45)

**Status of this document: characterisation of the ORIGINAL code. Nothing has moved. No weapon-execution responsibility has been extracted, no host boundary exists for it, no shipping build changed, no full pack was run.** Task EEDCS-45 (under EEDCS-18), branch `codex/d2-weapon-execution` (PR 104),
from accepted integration `04bf645a96f8277ca54d4a575b77f35b5ee68052` composed with the reviewed aiming candidate (runtime frozen at `52206fef3`; aiming EEDCS-44 is not accepted yet and its delivery precedes this task). Scope authority is the live M5 goal (Confluence 11534337 v3) and
the migration ledger (14548994 v38): physical aiming and weapon execution are the host's; target/weapon/package selection, the decision to fire, accounting and consequences stay in EECH_DC. Combat damage and resolution are the *following* D2 responsibility and are not characterised here.
Artifacts: [`reference/d2-weapon-characterization/`](../reference/d2-weapon-characterization/README.md).

This document records what the original code does, measured through the real host Lua -> public native module path during game stepping, what it was **not** shown to do, and where the physical and campaign parts are interleaved. It proposes the first bounded physical seam as an observation, not a design.

## Active call paths (verified in source, then measured)

| Entry | Called by | What it is |
|---|---|---|
| `generate_ballistics_tables`, `generate_guided_missiles_tables` (`wn_move.c`) | `init.c` at boot, once | the projectile simulation that produces the unguided ballistic tables (handed to the host raw through `campaign_aim_supply_table`) and the guided-missile range runs (which write only a text file) |
| `launch_client_server_weapon` (`wn_creat.c`) | the family fire code: `ac_wpn.c`, `fw_wpn.c`, `hc_wpn.c`, `vh_wpn.c` (AI aircraft/vehicle fire and AI decoys), `ac_anim.c` (Hokum crash debris), `ev_debug.c`, the player `ah_wpn.c`/`ha_wpn.c`; `aa_wpn.c`, `rv_wpn.c`, `sh_wpn.c` are dead code | the **campaign's decision to fire** has already been taken by the caller; this function turns it into one or more creation attempts |
| `create_client_server_entity_weapon` -> `create_local` | `launch_client_server_weapon`; `en_comms.c` (client messages, unreachable here) | salvo/rate-of-fire gating, ammunition accounting and notifications interleaved with the physical birth |
| `create_server_entity_submunition_weapon` | `weapon_movement` (fuze timer of a conventional-munitions weapon) | submunition births at the parent's pose and velocity |
| `update_server` (`wn_updt.c`) | the entity update list, once per weapon per frame | order: kill-next-update check, `weapon_movement`, animation, decoy update, killed effect, `kill_next_update` |
| `weapon_movement` (`wn_move.c`) | `update_server` | lifetime and expiry, guidance and lock source, guided/unguided step, contact, map bounds, terrain, terminal kill code |
| `collision_test_weapon_with_any_target`, `collision_test_weapon_with_trees` (`wn_cllsn.c`) | `weapon_movement` | contact queries; both call the line-of-sight collision machinery (terrain/object lookups: D3 coupling). `collision_test_weapon_with_given_target` has **no caller** (dead code) |
| `weapon_damage_capability`, `get_local_entity_armour_thickness` (`damage.c`, `wn_cllsn.c`) | combat code on a hit | combat resolution: the next D2 extraction, not characterised |

## Method

A gated observer (cargo feature `weapon-fixture`, macro `EECH_WEAPON_FIXTURE`, never shipping): `mb_wpnfx.h` hooks in `wn_creat.c`, `wn_move.c`, `wn_updt.c` and `wn_cllsn.c` (two **wrapped** functions, `weapon_movement` and `create_client_server_entity_weapon`, whose original bodies are renamed behind a feature-only macro; the rest are single statements between original statements),
`csrc/eech_wpn_fixture.c`, engine entries in `eech_engine.c`, Lua driver `lua/weapon-characterization.lua`, and the controlled launch witness `lua/weapon-case.lua`. It folds what the campaign's own update loop makes the code compute into **five separate hashes**, plus counters, measured value ranges, per-weapon and per-table rows, sample records,
and an **ordered, drained event log** (every table summary, launch outcome, birth, terminal and destroy, with exact `%.9g` values):

| hash | what it separates |
|---|---|
| `table` | the boot-time projectile simulation (every simulated flight: pitch, range-mark fill, step count, end time) and the tables themselves as the exact float bits handed to the host; the end state of every guided-missile range run |
| `launch` | each weapon's physical birth: velocity, lifetime, decoy/fuze timer, position, attitude (with the dispersion rotation), burst/lock-on/phase flags, parent kind, and the number of draws it took from the shared random stream |
| `flight` | every `weapon_movement` call: the path mask (which branches ran), guidance type and whether a target position was produced, the intercept prediction and guided-turn terms, contact queries, and the position, velocity, motion vector, attitude, lifetime, kill code and phase it left |
| `terminal` | each weapon's terminal fact: kill code, the whole trajectory's own hash and step count, final state, parent and target kinds (what the combat code consumes next) |
| `decision` | the campaign's part: salvo size, launch attempts and their outcome (created / no ammunition / rate-of-fire gated), guidance-source and validity decisions, and the per-update stage order |

No hash, event or sample carries an entity pointer, index, heap address or seed. The fixture numbers weapons itself (`w=`), in birth order, from a private table keyed by the entity address that never leaves the file; the shared random stream is observed only by the number of draws between two points (stepping a local copy of the generator). A hook only reads values the original has already produced, and
**never reads an output the original left unwritten on the path taken** (a guided target position is read only when `get_target_position` reported it valid; the lead solver's time of flight is not read at all). The system clock the weapon code reads (`timeGetTime`) is the host's simulated millisecond clock, so time-dependent expressions are deterministic here.
Draws from the **per-entity** seed (`get_client_server_entity_random_number_seed`: muzzle-velocity error, cruise-time error, jammer/smoke offsets) and the **shared** stream (`sfrand1norm` dispersion, `sfrand1` fuze jitter, `frand1` in spiral flight) are different things and both matter to a cut.

The Lua driver boots the campaign through the public path (`require ("eech_dc")`, the required reference-host callbacks), runs frames, and ends at the **first frame whose clock reaches the requested endpoint** (not after a precomputed frame count: the clock accumulates in float, and a 30 s smoke run took 301 frames). It reads the run-wide report at 60 s checkpoints and the end, and drains the ordered log at each. There is no probe: no weapon function is called from outside the game's own order, except in the one explicitly controlled witness below.

## Results

### Boot-time table generation (identical in every run, hash `table 77ed8877e2d2f252`)

`generate_ballistics_tables` simulated **9,047 unguided flights** (6,473 filled their whole range table, 2,574 ended early and the original copies the last cell into the tail: 561,800 tail cells) in **5,065,448 integration steps** of `move_unguided_weapon`, producing **41 weapon tables** (12,427,000 float cells, **0 non-finite**) that are handed to the host raw. The OTO Melara 76 mm table has 83 flights and none fills its range (all short). Velocity tests 1 to 4 of surface-to-air/surface-to-surface weapons are `memcpy` copies of test 0 and run no simulation.
`generate_guided_missiles_tables` ran 32 guided types: 32 zero-pitch range runs and **29** aimed runs (the other 3 return before simulating: not air-to-air/air-to-surface/surface-to-air). It writes only `guided-missiles-data.txt`; no table results from it. Both generators also write text files into the working directory (`ballistics-data.txt`, `guided-missiles-data.txt`), a transitional side effect.

## Findings of the characterisation (original behaviour, not corrected)

1. **Physics and policy are interleaved in the creation function.** `create_client_server_entity_weapon` mixes the rate-of-fire gate (the launcher's `weapon_salvo_timer` against the host's clock, which also sets the burst size), ammunition accounting, the `ENTITY_MESSAGE_ENTITY_FIRED_AT` notification to the target's force, sound and speech with the physical birth. `create_local` then holds the physical part: parent forward velocity, muzzle velocity plus a per-entity-seed error, the detach pose from the launcher's 3-D model (`detach_local_entity_weapon`: a model lookup), the fuze/decoy timer, and dispersion. Gated launches (450 here) return before any birth: a boundary around the creation call is called more often than it creates.
2. **The fuze timer asks the host's lead solver.** For weapons with a high-explosive anti-aircraft or conventional-munitions warhead and no guidance, birth calls `get_lead_and_ballistic_intercept_point_and_angle_of_projection` (already host-owned after EEDCS-44) and then draws one `sfrand1()` jitter from the shared stream; each of the 143 solved births drew exactly 2 values in that block (the lead solve and the jitter together; the split is not separately observed). A cut must keep that draw order.
3. **`weapon_movement` writes campaign state.** `check_guidance_source` rewrites the weapon's `LIST_TYPE_TARGET` parent when the launching human's target or laser lock changes; a contact with a different target switches the target parent before the hit; the smoke-grenade ground impact creates the killed-explosion effect from inside movement. Reached here: the guidance-source function ran 20,881 times and never changed a target (AI launchers only); the contact-switch path is a source-only fact.
4. **Kill codes are set in four places by physics** (lifetime/self-destruct, guided too-close and overshoot, contact, bounds and terrain); `update_server` then calls the killed effect (the combat entry) and marks the weapon for destruction the next update. The physical terminal fact and the combat consequence are separable at `update_server`.
5. **Shared-stream consumers.** Births with dispersion (`sfrand1norm`, two draws), the fuze jitter, and `frand1` in the spiral flight of some guided weapons draw from the shared stream; flight steps drew from it in 1,631 of 342,014 calls (always 2 or more; sampled steps show 2 for beam-riding and 12 for a guidance-none step, so more than one consumer exists and the split is not separately observed). Muzzle error, cruise-time error and jammer offsets use the **entity's own** seed, which must not become a public identity.
6. **Resting weapons.** A weapon that survives ground impact (smoke grenade) is not moved again but still ends by lifetime; a crate (511 s) is in flight for most of that time. Weapons outlive a bounded observation: the live report at the end of a run lists them.
7. **Table generation is a hot, deterministic boot cost:** 5.07 million steps and 12.4 million cells, writing two text files as a side effect.
8. **Original defects noted, not fixed:** none was found to change a result here. The flight-path deviation of some guided weapons (`update_guided_weapon`) reads `get_system_time`; here that is the host's simulated clock, so runs repeat byte for byte, and it would not under a real wall clock (a host boundary must supply that clock).

## Not reached, and why (stated, not covered)

Natural and controlled runs together did **not** reach: the map-area and ceiling bounds paths (`out_of_bounds` kill code 0), the Hellfire lock-on-after-launch climb/dive profile (needs a launcher with the lock-on-after-launch flag), the guided too-close kill, in-flight tree contact hits (794 tests, 0 hits), a `conventional munitions` submunition spawn, the jammer (chaff/IR) target branches, the EO tracking point, an actual guidance-source target change, active-laser and wire-guided weapons, any player launcher or a launch with parachute-open crate logic beyond the one crate, person launchers, and the `create_failed` outcome. The player (`salvo_not_ai`) and client/remote paths do not exist in a headless AI run. `collision_test_weapon_with_given_target`, the client update and `aa_wpn.c`/`rv_wpn.c`/`sh_wpn.c` are dead code.
The hashes are equality evidence (float bit patterns folded into FNV-1a), not an independent oracle. These roots retain the verified retail 3D database and terrain. `eech_engine_prepare_installation` preserves the database when `cohokum/3ddata/textures.pal` exists (it does in every verified Lebanon root); `load_3d_terrain_game_data` loads the selected session terrain. The synthetic 3D writer is a fallback for roots without that palette, not the path used by these runs. This is headless regression evidence, not a visual inspection of the retail game. One scenario, one seed, one map; Georgia was not run.

## The first bounded physical seam (observed, not a design)

Derived from the behaviour above, in order of risk:

1. **The flight integrators and the table simulation share one kernel.** `move_unguided_weapon`, `move_guided_weapon`/`update_guided_weapon` and the drag/weight functions are pure functions of a weapon's state, `delta_time`, a few database figures, the wind and air density at the point, and (for guided weapons) a target position. They are the physical heart of 342,014 flight calls and 5.07 million boot steps, and the table generator calls the very same function. A host-owned kernel for one flight step (state in, state out, with wind/density/target position as explicit lookups) would move the largest physical responsibility and the table production together, keeping the shared-stream draws and the float expression order. Wind and density are explicit D3 lookups.
2. **The terminal decision** (contact with a target, map bounds, terrain impact class) stays an explicit lookup coupling to D3 terrain/object services; the host would receive the weapon's old and new positions and answer the first contact, as it does for line of sight today.
3. **Birth kinematics** (parent velocity, muzzle error, dispersion, detach pose) is a separate, smaller stage that must preserve the draws and the lead-solver call order.
Campaign policy stays in EECH_DC: the fire decision, salvo and rate-of-fire gating, ammunition, notifications, target-link rewrites, the killed effect and destruction. Combat damage follows this extraction.

## Reproduce

From `eech-campaign/` at a clean checkout of `aaceb0e7d`: `sh tools/build-windows-weapon-fixture.sh target/weapon-fixture/<dir>` with a fresh `EECH_WIN_TARGET`; fresh private roots; `tools/weapon-characterization-windows.ps1 -Bin <dir> -Root <root> -Out <out> -Seconds 600` (one native process per root); `tools/weapon-case-windows.ps1` for the controlled witness; compare with `tools/wpn-trace-compare.py`, verify with `tools/wpn-case-verify.py`, read with `tools/wpn-trace-summary.py`. The 900 s control is `campaign.lua hours=0.25 record_every=10 checkpoint_every=3600 observe_every=60 observe_supply=0` against the retained ab-base files (`controls/ab-compare.py`). The queue scripts in `reference/d2-weapon-characterization/controls/` record each run's actual exit.
