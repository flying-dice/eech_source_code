**Before moving existing behaviour:**
1. Reproduce the behaviour on a named baseline revision.
2. Protect it with sociable tests of real collaborating components. Control environmental inputs, not the campaign decisions being asserted.
3. Record what passes, known defects, unsupported cases and unavailable prerequisites.
4. Work on a dedicated Task branch and PR.
5. Keep structural moves separate from rule changes, fixes and balancing.

**What a pure refactor must prove.**
- Characterisation tests that passed before the move still pass after it. No artificial red step is needed.
- The newly established ownership contract holds. Host observations demonstrably influence the campaign, and host actions are demonstrably used. Interface declarations or recordings don't prove this.
- Integrated host-Lua → public native module → world evidence is preserved, since private Rust or C tests can't substitute for it.
- There is no hidden shared world authority.

**Who approves a PR.** A current formal GitHub **APPROVED** review from `@fd-starscream-bot` is required. The reviewer's actual login must be verified. Comments, review requests, other approvals, green CI and agent self-reviews don't count. New commits after approval need fresh approval. The PR author must be a different identity from the lead.

**When the M4 regression pack differs.**
- A red pack produces a proposal, not a new baseline. Nothing re-records baselines in place, and `-Update` is refused.
- Run `baseline-governance.py propose`. Every failure starts as `UNCLASSIFIED`.
- Classify each delta with evidence as exactly one of four classes:
  - `regression`: rejected, and the candidate stays failing.
  - `approved-defect-correction`.
  - `intentional-semantic-change`.
  - `expected-input-world-variation`: this founds a separate lineage and never replaces the equivalent-input baseline.
- The PR carries the before-change report, the change record and the old and proposed baseline identities. The lead approves the commit that holds that exact record.
- A follow-up commit adds the `approval: {pr, review_id, commit}` reference and runs `adopt`. The tool checks the review on GitHub, and the new commits need fresh approval.
- A disposition explains a difference and never makes a failing check pass.
