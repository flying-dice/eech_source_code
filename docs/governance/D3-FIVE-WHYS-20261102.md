# D3 delay: five whys and corrective actions

Owner: Starscream. Date: 2 November 2026. Task: EEDCS-53.

The avoidable delay was a delivery-control failure. Byte-identical regression and
independent review remain requirements; they are not the root cause to remove.
Terrain/ground/environment increments have shipped, but Task52 preparation has
not yet changed production target-point routing. Long regression wall time is a
separate, real scheduling constraint.

| Why | Finding supported by the work |
|---|---|
| 1. Why is D3 not delivered? | Required production spatial/model work remains coupled, while Task50's long full pack is still running. Task52 has produced preparation instead of a production cutover. |
| 2. Why did preparation dominate? | Original branch capture, fallback setup, two host numeric kernels and repeated harness repairs were handled serially. Passing preparation was too often treated as the next destination. |
| 3. Why were repeated repairs needed? | The first capture contract emphasized branches/outputs and omitted replay inputs and initializer side effects: base position, live scale/chain and CRT draws/reseeds. Synthetic fixture evolution then exposed format and history inconsistencies. |
| 4. Why did that not trigger a smaller cutover sooner? | There was no enforced preparation limit, explicit next production commit or fixed distinction between a correctness blocker and optional diagnostic hardening. Review findings were useful, but the coordinator allowed the work to keep expanding. |
| 5. Why did this survive continuation? | Handover state accumulated duplicated histories and stale entry points. One `D3-NEXT-ACTION.json` still described October31 work while newer state lived elsewhere. The session could resume activity without a compact, authoritative delivery decision. |

The lead owns these process failures. The independent review found real defects
(including legitimate empty-slot semantics and RNG-report joins); bypassing it
would conceal them. The correction is earlier contract completeness, bounded
iterations and faster production increments, not weaker evidence.

## Improvements applied

| Control | Concrete implementation | Evidence of use |
|---|---|---|
| Production action first | Mandatory active extraction card names host offset initialization and its exact blocker. | AGENT startup link; ACTIVE-EXTRACTION.json. |
| Stop expanding preparation | Two-batch limit; beyond it, only a named blocker can justify another characterization. No automatic user permission step. | migration-progress.py rejects an unmotivated characterization and blocked cutover. |
| Batch work and reuse evidence | One author corrects the consolidated RNG group. The comparer-only correction joins the next production implementation; closed numeric evidence is retained. | Current Task52 decision recorded in the card. |
| Recover from one current record | Compact live checkpoint; older names become pointers; useful histories archived. | Runtime checkpoint location in EXECUTION.md, not copied into every source document. |
| Honest progress and ETA | Distinguish preparation, cutover, authority, full conformance, review and merge. Use simulated time for run ETA; do not use recording byte fraction as a clock. | Required report fields and explicit acceptance gates. |
| Protect the baseline while reducing waste | Focused green/fmt before one freeze; source-based reuse; one cache owner and combined-log writer; no restart on timeout. | Existing regression skill/runbook retained and made part of this execution sequence. |

## Learnings to carry forward

- A numerical match is valuable but does not establish production ownership.
- Characterization needs enough **input** data to replay the actual contract.
- Shared RNG and FPU/state writes must be inspected before deleting constructors.
- An observer needs trustworthy validation, but every extra guard must serve the
  blocked extraction; diagnostic completeness is not an independent product.
- Repeated green tests and evidence publication do not substitute for a merged
  increment. Report the missing production change plainly.
- Preserve failures and immutable identities, but move history out of the recovery
  path. Compaction should recover the next action, not restart the investigation.
- An observer must follow the ACTUAL nested callback order and every placement stage of the funnel it
  observes (a call that nests the host's statement before it returns; a record that is placed twice), and the
  test must bind that source order before the freeze, from the staged source and not from a preferred
  sequence. A green recorder-only sequence does not establish the public funnel.
- Diagnostic capacity must cover the real boot-placement demand of the declared window and keep
  incomplete-as-failure: an overflow is counted, never sampled or waived; a green prefix of a truncated
  report is not a baseline. Size a bound from the measured attempted records, not from a sequence number
  that also counts aggregates.
- Authoritative machine-readable, fully sealed records outrank display headers: a tool that reads a build
  record parses its section markers, not a generic digest-looking substring. (Root's profile-reader failures
  were a tooling lesson, fixed in the profile audits; not a product defect.)
- When a raw word moves to the host, every classifier of that word is part of the move: a check that demands
  every fact be finite (the integer classifier and its floating mirror alike) silently turns a valid raw
  domain (a restored negative, infinite or NaN word) into a refusal. Audit and pin both, with the exact
  words, before the first question carries the word. Detect an arrival by the key the insertion issued,
  not by a record's first statement: records merge, keys do not.
- A move changes the entry point of an accepted control, not its scenarios: keep the original body compiled
  in the profile that keeps the original solver, run the accepted expectations there unchanged, and add the
  differential of the host's expression beside it; a retired field is never read or written in the hosted
  build (pinned by a census guard), instead of being kept as a mirror that can go stale.
- A claim of literal equality is checked against the actual Git bytes (`git cat-file`), not a hash-object label: filters make the label differ from the bytes without touching them (three inherited CRLF test
  files differ raw-versus-Git; four Core files differ only as filtered labels). Say which, and never normalise.
- Derive a batch's completion from the actual whole batch (every child, its exit and its output), not from the last child or a summary line; a controlled test that manufactures a protocol phase is a boundary
  check, and a plan that cannot be run (no command, no row schema, no eligibility, no expected outcome) is not a plan.
- An expected error string is only evidence when the run reached the actual eligible intervention it describes: credit a refusal only with exactly that one intervention (height_altered=1), whatever the
  secondary input altered and whatever marker the engine stopped at; any fatal before it is a failure, even one bearing the expected marker, and only a clean run with no eligible read is UNREACHED. A
  matching marker string does not prove the cause.
- Scoped whole data needs unique, complete rows and a terminal verdict on BOTH sides of a comparison: a green prefix is not a whole scan. Validate the accepted report and the live one as whole (verdict last, declared
  count, unique contiguous indices and sector keys, totals equal to the rows, exact fields and domains) before comparing, keep the hosted scope narrower than the original's, and run single-fault controls from a
  coherent positive; check the real retained report against the same rules, not only scripted fixtures.

Success is the next reviewed production increment with unchanged accepted runs.
This process task itself changes no campaign runtime, baseline or tolerance and
does not justify another full regression run.
